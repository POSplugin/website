[ 03 ] How it works

Three layers. Zero glue code.

Hover or tap a unit to open it.

IN POS·APOS·BPOS·C+ new POS
RU-01

Connector layer

  • OAuth, API keys and partner credentials
  • Polling or webhooks, with retries and rate limits
  • Templates for REST, GraphQL and file exports
RU-02

AI mapping engine

  • Reads API docs, specs or sample payloads
  • Confidence score on every field
  • Every confirmed mapping trains the next one
RU-03

Unified API + webhooks

  • One REST API, one event stream
  • Original POS payload kept on every record
  • Two-way where the POS allows: inject orders
HM · ALWAYS ON

Health monitoring

drift: amt → amount_cents
fix suggested
  • Detects schema drift and failing syncs
  • Suggests a mapping fix before customers notice
  • Alerts ops with what broke and why

[ 07 ] Trust & security

Boring about security. On purpose.

> Designed in from the first line of code. PosPlugin is in early access, so none of this is audited yet.

No card numbers

We never receive full card numbers, only brand and last four as the POS returns them. Designed to stay out of PCI card-data scope.

Encrypted everywhere

In transit and at rest. POS credentials live in a secrets vault.

Per-tenant isolation

Your merchants' data never mixes with anyone else's.

Full audit log

Who changed which mapping, and when. Every AI decision too.

Built for GDPR

Data export, deletion and regional storage options, with a DPA that lists every sub-processor.

> AI proposes. Humans confirm. Low-confidence mappings never go live alone.
